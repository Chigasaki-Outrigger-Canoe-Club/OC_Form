## 1. 目的

- 自分のパドリングフォームを動画から解析し、技術の改善に役立てる。
- 最終目標：日本トップレベルのアウトリガーカヌー選手と自分のフォームを比べる。各選手の3Dモデルや、骨格推定を重ねた動画を並べて見比べる。
- 追加費用は原則ゼロ。GitHub Pages（静的サイト）の構成を続ける。

## 2. 前提（選手・撮影）

- 選手：Manato（身長166cm、体重70kg、パドル49inch＝PILIの涙形ブレード）。エルゴはアウトリガー用に改造した Concept2 RowErg。
- 漕ぎの途中でパドルチェンジ（左右の交代）をする。
- 撮影：前・左・右・後ろの4方向。**同時撮影ではない**（1方向ずつ撮る）。
- 足の置き方：両足を前でそろえ、かかと同士は拳1個分（約10cm）。内股にはならない（後ろから撮る場合も同じ）。
- 動画（2026-10-24）：H.264、720p、30fps、約30秒。前・右は縦長、左・後ろは横長。

## 3. 方向ごとの見え方（ユーザーの観察）

| 方向 | よく取れるもの | 弱いもの |
|---|---|---|
| 右・左 | 漕ぐ側の手・体・脚、目線、反対側の手の高さ。関節の位置全般 | カメラと反対側（上の手の側）。左右の倒れ |
| 前 | シャフトの角度（両手の位置）、肩の位置、体の倒れ具合 | 手が重なると体の推定が難しい |
| 後ろ | 体の左右の傾き、骨盤・肩の高さ | 前後の倒れ。手首（ほぼ見えない） |

## 4. 決定事項（食い違う指示の整理）

| 論点 | 指示の経緯 | 採用 | 理由 |
|---|---|---|---|
| 4方向の統合 | 「4方向の強みを合成して平均の漕ぎに」（10/24）→「キャリブレーションなしに単純平均しない。できなければ方向ごとに比較表示」（10/24 夜） | **方向ごとの結果の比較表示を基本**にする。「3D：平均の漕ぎ」は残すが「キャリブレーションしていない推定」と明記し、使った方向を表示する | 同時撮影ではないため三角測量はできない。根拠の弱い値で技術判断をしないため |
| 3Dの作り方（最新・①で実装） | 「前後はシャフトの角度だけ」（10/24 23時）→「4カメラを平均しない。関節ごとに採用するカメラを切り替える。肩は前後優先、骨盤は後ろ優先、左右の傾きは前後」（10/24 23:30） | **関節・軸ごとに担当カメラを決める**（下の「3Dモーション生成」）。前後の奥行き（Z）は使わない | 後の指示を優先。前後を混ぜて動きがおかしくなったのは、奥行きと手首・肘まで混ぜていたため。奥行きは横だけにする |
| 平均の漕ぎの重み | 「体全体は横」→「前はシャフトと手首、後ろはシャフトと肘・肩の高さ」→（10/24 夜）「前後を組み合わせると実際と全く違う。前後はシャフトの角度だけ、3Dは左右の横から」 | **3Dモデル（関節）は左右の横の動画だけ**。前・後ろは**シャフトの角度だけ**。横の動画がその漕ぎ側を撮っていないときだけ、前・後ろも関節に使う | 後の指示を優先。実際の動きと違うという観察に基づく |
| 動画の保存 | 「動画は保存しなくていい」→「動画もGitHubに残したい」 | 動画は**小さくして（長い辺960px）GitHubに保存**。既定でオン。公開されることを明記 | 後の指示を優先。元の大きさ（60〜70MB）だと無料の容量がすぐ埋まる |
| 速さと精度 | 「計算を速く」→「速度より推定を細かく」 | **精度を優先**（heavy モデル＋手の専用推定）。読み込みは順番に読む方式で速くする | 後の指示を優先 |
| 平滑化・補正 | 「ぎざぎざを直して」「ありえない動きは除外」→「平滑化だけで精度が上がったと判断しない」 | 平滑化・補正は使うが、**生の推定と処理後を切り替えて見られる**ようにし、良し悪しは**手で付けた正解との誤差**で判断する | 両方を満たす |
| 3D座標 | 「3Dモデルをきれいに」→「world landmarks は推定値。実測と表示しない」 | 3Dは「推定値」と明記。縦・横は2Dの骨格に合わせ、奥行きだけ world を使う | 頭の角度が2Dと最大37°違ったため |
| 人の手による補助 | 「10フレームくらい手伝える」→「4場面は人が設定」→「20〜30フレームの検証用データ」 | 2種類に分ける。**骨格の調整**（推定を直す。4場面×左右）と、**正解フレーム**（評価だけに使い、推定は変えない。20〜30フレーム） | 評価に使う正解で推定を直すと、評価にならないため |
| 選手データ | 「バックアップ機能」→「バックアップは不要、自動で」 | GitHubへ自動保存・自動で戻す。手動のバックアップは削除 | 後の指示を優先 |
| Concept2 の CSV 読み込み | 「Concept2 を読み込んでグラフに」→「読み込みの場所は一旦不要」 | サイトの欄は**削除**（js/erg.js・erg-view.js は残す）。PM5 を USB で記録する Python ツール（tools/pm5）は残す | 後の指示を優先。「一旦」なので戻せるようにコードは残す |
| ストロークの区切りの編集 | 「キャッチを手で設定」→「設定が難しいので削除」 | ストローク欄・編集を**削除**。区切りは自動検出だけ（内部では使う） | 後の指示を優先 |
| GitHub のトークン | 「毎回入力なので連携できないか」 | ブラウザに保存（貼り付けた時点）＋保存済みの表示。GitHub ログイン連携は見送り | GitHub Pages だけではログイン連携（OAuth）に必要な秘密の鍵を置けない。サーバー（Cloudflare Worker など）が要る |
| GitHub に保存する骨格 | 既定は平均の3Dモデルとストロークだけ | 既定でも**2Dの骨格（pose）を入れる**（1方向 約1MB） | 選手を並べて比べるとき、動画に点を重ねるため |
| 人物を拡大して推定 | 改善案として提案 | 実測では**悪化**したため採用しない（5章） | 比較結果で判断 |

## 5. これまでの実測（2026-10-24 の4本、MediaPipe Python 版・CPU）

- 人物の大きさ（画像の高さに対する割合）：前 79%、左 55%。
- lite・full・heavy の比較（正解なしの指標：跳び＝1フレームで胴の長さの25%以上動いた回数）
  - 手首の跳び：前 226 / 159 / 142、左 87 / 70 / 25、右 39 / 28 / 40
  - ほとんどの部位で heavy の揺れが最も小さい。ただし右の手首・肘は full のほうが跳びが少ない
  - 1フレームの時間：22 / 30 / 77 ms
- 人物を切り出して拡大（heavy）：前はほぼ同じ、左は悪化（手首の跳び 25 → 52、肩・腰にも跳びが出た）→ 採用しない
- 後ろの動画：手首の信頼度が 0.5 未満のフレームが 85〜94%。ストロークを検出できない
- presence：Python 版では取れるが、ほぼ常に 1.0 で差が出ない。ブラウザ版（tasks-vision 0.10.14〜0.10.22）は visibility しか返さない
- 後ろの動画の肩の傾き：周期 33〜34 フレーム（横の動画のストロークの中央値 33・34 と同じ）。肩の信頼度は 1.0、肘は 0〜0.1
- 後ろの位相合わせの基準：前の動画と重ねると相関 0.93（右漕ぎ）／0.72（左漕ぎ）。横の動画どうしは右漕ぎで −0.25 と食い違い（横からは奥の肩が隠れる）→ 基準は前にした
- 新しい統合（10/24 の4本、heavy）：肩＝前・後ろ、肘・手首・膝＝横、骨盤＝後ろが担当になり、信頼度は肩・骨盤 1.00、カメラ側の肘・手首 0.87〜0.96、反対側 0.70〜0.75
- 3Dモデルの点のずれ（10/25）：前の動画は足が艇（エルゴ）に隠れて床の推定が約45cmずれ（腰の高さ 0.77m、横は 0.28〜0.32m）、前・後ろを担当にした肩が横だけのときより最大28cm高くなっていた → 各動画の点を「腰の中心からの位置」にしてから合わせ、腰の中心は横の動画で決めるよう修正。横だけとの差は肩で最大8cm（左右の傾きの分）に
- **注意：上の数字は「安定さ」の目安で、正しさではない。** 正しさは正解フレームとの誤差で判断する（未実施）

## 6. 機能の一覧（2026-10-24 時点）

- 骨格推定：MediaPipe Pose Landmarker heavy（float16、GPU）＋ Hand Landmarker（両手）。前・後ろは画像から木のシャフトの線も探す
- 実行の流れ：骨格推定 → 骨格の調整（4場面×左右、人が合わせる）→ 3Dモデル → 保存（ブラウザ内＋GitHub）
- 3Dの作り方：2Dに合わせる → 外れ値を外して補間・平滑化 → 選手基準（X左・Y上・Z前、m）→ ありえない形を直す（constraints.js の LIMITS）→ 脚・足の置き方
- 表示：動画、3D（平均の漕ぎ）、動画と3Dを並べる（1方向の推定なので参考程度）
- 推定の確認：関節ごとの品質の表（信頼度・跳び・ぶれ・同じ位置のばらつき・正解とのずれ、生→処理後）、正解フレームを付ける機能、信頼度での色分け
- 改善点のコメント：OC研究（Sealey 2011、Canyon & Sealey 2016）、OC指導資料、ボートの考え方（World Rowing）を根拠として表示
- 保存：ブラウザ内（IndexedDB）と GitHub（data ブランチ、公開）。スマホは開くと一覧が出る（トークン不要）
- 選手を並べて比べる：保存した動画＋骨格を、ストロークの同じ位置でそろえて並べる（PC 4人、スマホ 2人）
- Concept2（PM5）：USB で記録する Python ツール（tools/pm5）。リアルタイムの波形表示、CSV（1本ごと・全測定値・波形つき）。サイトの読み込み欄は一旦削除

## 7. 評価の方針

- 正解フレーム（人が関節の位置を付けたもの）を 20〜30 フレーム用意し、モデル・処理ごとに **平均誤差・中央値・失敗率** で比べる。
- 信頼度が上がった、揺れが減った、だけでは「精度が上がった」と判断しない。
- 取得できない値（例：ブラウザ版の presence）は推測で補わず、「取得できない」と表示する。

## 8. 次にやること（2026-10-24 夜の指示）

最初の成果物は「モデル比較と推定結果の可視化」まで。評価してから次の改善を決める。

1. Lite・Full・Heavy を切り替えて比べるモード（同じフレームを各モデルに入れる）

3. 人物の大きさ・余白・解像度の条件を比べる（全身を切らずに拡大した場合も）
4. 問題のあるフレームの一覧（信頼度が低い、急に動く、隠れている）
5. フィルタの前後の切り替え（実装済みの「生／処理後」を使う）
6. 20〜30 フレームの正解との誤差（平均・中央値・失敗率）をモデルごとに表示

### 3Dモーション生成（10/24 23:30 の指示。①を実装、②③は未着手）
- 対象：「3Dモデル」ボタン（旧名「3D：平均の漕ぎ」）を押したときの表示
- 4カメラの結果を平均しない。関節ごとに採用するカメラを切り替える（担当＝優先、ほかは補助として信頼度で重み付け）
- 担当：手首・肘＝横（前後は補助）／肩＝前・後ろ（横は補助）／骨盤＝後ろ（横は補助）／体幹の前傾＝横だけ／体幹の左右の傾き＝前・後ろ
- 側面の役割：上下肢の関節位置、前後の動き、キャッチのリーチ、前傾後傾、肘角度、脚。前面：肩の左右位置、胴の左右傾き、シャフト角度、上の手と下の手の位置関係。背面：肩・骨盤の高さ差、胴の左右傾き、シャフト角度
- パドル：MediaPipe の手首から推定しない。別のオブジェクトとし、上の手と下の手の位置からシャフトの向きを作る
- 手動補正：前面の動画で上の手・下の手の2点をドラッグ → シャフト角度を再計算。補正点はキーフレームとして保存し、間は補間
- 出力：Blender / Unity Humanoid に使える3D関節データ。関節ごとに使ったカメラと信頼度を記録。信頼度が低い関節は前後のフレームからならす
- 計画：①担当カメラの表で統合（関節・軸ごと、使ったカメラと信頼度を記録）②パドルを別オブジェクトに＋前面で上下の手をキーフレーム補正 ③BVH（Blender で読める。Unity は Blender で FBX にして Humanoid）と JSON を書き出し
- 課題：後ろの動画はストロークを検出できない（手首が見えない）ため、そのままでは位相をそろえられない
- **①実装済み（10/24 夜）**
  - 関節・軸（左右・上下・前後）ごとの担当カメラの表（js/fusion.js の ROLES）。重み＝役割（担当1・補助0.2・使わない0）×信頼度。前・後ろの奥行き（Z）はどの部位も使わない
  - 位相・関節ごとに「いちばん効いたカメラ」「その割合」「信頼度（0〜1）」を記録（fused.right/left.sources）。画面に部位ごとの担当と信頼度を表示
  - 信頼度の低い点は、位相に沿ったならしで前後の点に寄せる
  - 後ろの動画：肩の傾き（左右の肩の高さの差）でストロークを区切り（js/tilt.js）、漕ぐ側は肩の傾きで決め、前の動画の肩の傾きの曲線に重なるよう位相をずらす。前がなければ横を基準にする

### 動画の保存先（10/25 相談中）
- 状況：Reo を保存したが「選手を並べて比べる」に出ない。GitHub の data ブランチには 10/21 の Manato しかなく、Reo の分は解析結果も選手データも届いていない（GitHub への送信が失敗、またはトークン未保存。「保存の設定」の表示で原因を確認）

  - GitHub に動画を置き続ける場合：公開リポジトリなので誰でも見られる。リポジトリは 1GB 程度までが目安（約40回分）
  - **決定（10/25）：お試しなので GitHub のまま**
